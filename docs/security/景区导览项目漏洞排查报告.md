## 3. A 类：已实际验证的问题

### S-1【高】公开仓库当前文件明文包含 API Key 与旧 JWT 密钥

- **验证方式（已实际执行）**：拉取公开原始文件
  ```bash
  curl -s https://raw.githubusercontent.com/4evour/Scenic_spot_guide_system/master/scripts/cleanup-git-history.sh | sed -n 12,15p
  ```
- **实际输出（已脱敏，原文是完整明文）**：
  ```
  cat > "$EXPRESSIONS_FILE" << 'EOF'
  sk-[已打码]…(共 32 位十六进制)…[已打码]==>REDACTED
  [已打码]…(共 64 位十六进制)…[已打码]==>REDACTED
  EOF
  ```
  第 13 行是 `sk-` 开头的 DeepSeek 风格 API Key（首次提交信息写的是"AI聊天功能（DeepSeek API）"），第 14 行是旧的 64 位十六进制 JWT 密钥。
- **泄露时长**：`list_commits path=scripts/cleanup-git-history.sh` 显示，该文件在提交 `df23501`（2026-06-13 16:24 北京时间，信息为"新增 .env.example 和 cleanup-git-history.sh"）加入，至今一直公开，已超过 3 个月。仓库是 public，任何人都能看到。
- **讽刺之处**：这个脚本本来是"从 Git 历史中清除泄露密钥"的，却把要清除的密钥原文写进了脚本再提交上去。`SECURITY_PUBLIC_RELEASE_REVIEW.md` 声称"当前跟踪文件未发现高置信度真实密钥"、"历史密钥扫描未发现 sk- 形态密钥残留"，与事实不符。
- **为什么 CI 密钥扫描没拦住**：`scripts/check-secrets.mjs:8-23` 的 `textExtensions` 只扫 `.go .js .ts .vue .md .yaml .yml .json .html .css .txt .toml .mod .sum`，**不含 `.sh`、`.ps1`、`.bat`、`.env*`**。第 26 行的 `sk-` 规则本身能匹配，但这个文件根本没被扫描。
- **预期结果**：公开仓库的任何文件都不应包含真实凭据；扫描器应覆盖所有文本文件。
- **代码位置**：`scripts/cleanup-git-history.sh:13-14`（另外第 34、40 行含密钥前缀片段）；`scripts/check-secrets.mjs:8-23`。
- **修复建议**：
  1. **立即**到 DeepSeek（以及 DashScope 等曾用过的平台）控制台吊销并轮换该 Key，查看账单和调用记录有没有被盗用。这一步比删文件重要：密钥已经公开 3 个月，只能当它已经泄露处理。
  2. 旧 JWT 密钥如果仍在任何环境使用，立即更换（更换后所有旧 token 失效）。
  3. 把脚本改成从本地未跟踪文件读取替换表（例如 `.git-filter-expressions.txt`，并加入 .gitignore），脚本里不写任何密钥。
  4. 用 `git filter-repo --replace-text` 重写历史并强推（**这会改写公开历史，需要本人确认后执行**）；同时在 GitHub 开启 Secret scanning 和 Push protection（`get_repository` 显示两者目前都是 `disabled`）。
  5. `check-secrets.mjs` 改为扫描全部文本文件（或按"排除二进制扩展名"的方式），并额外接入 gitleaks / trufflehog 这类成熟工具，同时扫历史（`gitleaks detect --log-opts=--all`）。

## 4. B 类：仅静态分析、未能运行复现的问题

### S-2【高】游客登录信任客户端指纹：凭指纹即可拿到他人游客账号；同型号设备指纹碰撞导致共用账号、互看对话

- **原理**：
  - `POST /api/v1/auth/guest-login` 豁免 CSRF（`middleware.go` 的 `csrfExemptPaths`），直接把请求体里的 `device_fingerprint` 当作身份凭证（`guest_handler.go:37-45`）。
  - `CreateGuestAccount` 用 `FindByGuestToken(fingerprint)` 查到已有游客就**直接签发该账号的 JWT**（`guest_service.go:42-49`），不需要任何秘密。
  - 前端指纹（`web-vue/src/utils/fingerprint.ts`）只由 UA、语言、分辨率、时区、CPU 核数、平台、Canvas 末 50 字符、WebGL 渲染器拼接后做 SHA-256。**同一型号的 iPhone/安卓机在同一系统版本下，这些值几乎完全相同**，景区现场大量游客会得到同一个指纹。
  - 不传指纹时退化为 `SHA256(IP|UA)`（`guest_handler.go:38-42`，`middleware.go` 的 `EnsureGuestMiddleware.Handle` 也一样）。景区 Wi-Fi 或运营商 CGNAT 下同 IP、同 UA 的游客同样会撞号。
  - 撞号后，`/api/v1/sessions`（`session_handler.go:40-62`）按 `user_id` 列出会话，**B 能看到 A 的全部历史对话**，还能删除（`DELETE /sessions/:id`）。
- **前置条件**：服务已启动（SQLite 即可，不需要 LLM key，本地兜底会生成回答）。
- **复现步骤**：
  ```bash
  B=http://127.0.0.1:8080
  FP=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa   # 模拟两台同型号手机算出的同一指纹
  # 游客 A
  curl -s -c a.txt -H 'Content-Type: application/json' -d "{\"device_fingerprint\":\"$FP\"}" $B/api/v1/auth/guest-login
  CSRF_A=$(awk '$6=="csrf_token"{print $7}' a.txt)
  curl -s -b a.txt -c a.txt -H "X-CSRF-Token: $CSRF_A" -H 'Content-Type: application/json' \
       -d '{"role":"user","content":"我叫张三，手机号13800000000，住在灵山酒店301"}' \
       $B/api/v1/sessions/sess-A-001/messages
  # 游客 B（另一台设备，指纹相同）
  curl -s -c b.txt -H 'Content-Type: application/json' -d "{\"device_fingerprint\":\"$FP\"}" $B/api/v1/auth/guest-login
  curl -s -b b.txt $B/api/v1/sessions
  curl -s -b b.txt "$B/api/v1/sessions/sess-A-001/messages"
  ```
- **静态推断的实际结果**：两次 guest-login 返回**相同的 `id` 和 `username`**（如 `guest_1a2b3c4d`）；B 的 `/sessions` 列表包含 `sess-A-001`，messages 接口返回 A 写入的隐私内容。
- **预期结果**：不同设备的游客应该是不同账号；指纹最多用作风控参考，不能当凭证。
- **代码位置**：`internal/handler/guest_handler.go:32-45,145`；`internal/service/guest_service.go:36-49`；`internal/pkg/middleware.go`（`EnsureGuestMiddleware.Handle`、`csrfExemptPaths`）；`web-vue/src/utils/fingerprint.ts:6-15`。
- **修复建议**：
  1. 游客首次访问时由服务端生成高熵随机 ID（`crypto/rand` 32 字节），存进 HttpOnly Cookie（或放在 localStorage 并以此换 token）。"恢复游客"只能靠这个服务端签发的随机值，**不能靠客户端可计算的指纹**。
  2. 如果一定要保留"换浏览器恢复"功能，就要求用户显式升级账号（已有 `upgrade-guest`）。
  3. 数据库里只存随机 ID 的哈希；指纹只用于限流和风控。
  4. 论文里把它写成"游客身份的威胁模型"一节，是一个很好的安全设计讨论点。

### S-3【中】TTS 接口无需登录、无限流、文本长度无上限

- **原理**：`tts_handler.go:193-196` 注册 `/api/v1/ai/tts` 和 `/ai/tts/stream`，**没有 Auth、没有 RateLimit**。文本只做了 `TrimSpace` 和判空（`tts_handler.go:51-55`）。全局请求体上限是 12MB（`routes.go:181-194`），`edge_tts.go:84,188` 会按 4096 字节把长文本切段，**逐段向微软 Edge 在线 TTS 发起请求**。一个 12MB 请求就能触发约 3000 次外部调用（受 30 秒超时截断，但仍会占用连接和 CPU），容易导致服务器出口 IP 被微软封禁，影响全体用户的语音播报。
  - 注：CSRF 中间件确实会要求 `csrf_token`，但攻击者先调一次 guest-login 就能拿到 cookie 并自己带上请求头，所以 CSRF 不能替代鉴权和限流。
- **复现步骤**：
  ```bash
  B=http://127.0.0.1:8080
  curl -s -c j.txt -H 'Content-Type: application/json' -d '{}' $B/api/v1/auth/guest-login >/dev/null
  CSRF=$(awk '$6=="csrf_token"{print $7}' j.txt)
  python3 -c "import json;print(json.dumps({'text':'灵山大佛'*50000}))" > big.json   # 约 600KB
  time curl -s -o out.mp3 -w '%{http_code} %{size_download}\n' -b j.txt -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' --data @big.json $B/api/v1/ai/tts
  # 并发：
  for i in $(seq 1 50); do curl -s -o /dev/null -w '%{http_code}\n' -b j.txt -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' -d '{"text":"测试"}' $B/api/v1/ai/tts & done; wait
  ```
- **静态推断的实际结果**：长文本请求被接受（200，或 30 秒超时后 500），日志中出现大量 Edge TTS 分段请求；50 个并发请求全部被处理，**没有 429**。（VM 如果不能访问微软服务，会看到 500 `msg_tts_failed`，但"未鉴权、无限流、无长度限制"这三点仍然成立。）
- **预期结果**：要求登录（至少是游客 token），限流（例如每用户 20 次/分钟），文本上限（例如 500 字）。
- **代码位置**：`internal/handler/tts_handler.go:44-62,86-104,193-196`；`internal/service/edge_tts.go:84,188`；`internal/handler/routes.go:181-194`。
- **修复建议**：`r.POST("/ai/tts", pkg.AuthMiddleware(), getRateLimitMiddleware(20, time.Minute), h.TTS)`；在 handler 里加 `if utf8.RuneCountInString(req.Text) > 500 { BadRequest }`；Voice 和 Rate 做白名单校验；对相同文本和音色的结果做缓存。

- **代码位置**：`internal/handler/ai_handler.go:227-237`；`internal/handler/ai_proxy_handler.go:118`；`internal/handler/digital_human_handler.go`（`ChatText` 的 `InputText`，同样没有上限）。

### S-5【中】游客账号可无限创建

- **原理**：任何新的 `device_fingerprint` 字符串都会创建一个新的 `users` 行，并对 16 字节随机密码做一次 bcrypt（`guest_service.go:52-78`）。限流只有内存版每 IP 10 次/分钟（`guest_handler.go:145`），多 IP 或 IPv6 很容易绕过；`/ai/chat` 路径上的 `EnsureGuestMiddleware` 还会按 `IP|UA` 自动建号，换 UA 就能再建。代码里**没有过期游客的清理任务**。
- **复现步骤**：
  ```bash
  for i in $(seq 1 10); do curl -s -H 'Content-Type: application/json' -d "{\"device_fingerprint\":\"fp-$RANDOM-$i\"}" http://127.0.0.1:8080/api/v1/auth/guest-login | grep -o '"id":[0-9]*'; done
  sqlite3 data/scenic_guide.db "select count(*) from users where role='guest';"
  ```
- **静态推断的实际结果**：输出 10 个递增的不同 id，guest 数量加 10；第 11 次开始返回 429（同 IP），换 IP 后可以继续。
- **预期结果**：游客建号有全局速率上限，过期游客定期清理。
- **修复建议**：游客不必立刻落库（可以先用签名 Cookie，产生会话时再创建）；定时清理 N 天未活跃的游客；bcrypt 对游客没有意义（游客不用密码登录），可以直接存不可登录的占位值。

### S-6【中】游客评分可匿名刷分、伪造报表、覆盖他人评分

- **原理**：`visitor_experience_handler.go:64-70` 的 `/api/v1/visitor/ratings` **没有鉴权**；`SubmitSpotRating` 用客户端提供的 `session_id` + `spot_id` 做 upsert（`visitor_experience_service.go:104-135`，repository 里用 `OnConflict`）。换一个 `session_id` 就是一票新评分；知道别人的 `session_id` 就能覆盖他的评分。`spot_id` 不校验是否存在，`comment` 没有长度限制。这些数据会进入管理大屏的"游客体验闭环"和"游客感受度报告"，**直接破坏系统核心的数据分析价值**。
- **复现步骤**：
  ```bash
  B=http://127.0.0.1:8080
  curl -s -c j.txt -H 'Content-Type: application/json' -d '{}' $B/api/v1/auth/guest-login >/dev/null; CSRF=$(awk '$6=="csrf_token"{print $7}' j.txt)
  for i in $(seq 1 100); do curl -s -o /dev/null -b j.txt -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' \
    -d "{\"session_id\":\"fake-$i\",\"spot_id\":1,\"overall_rating\":1,\"comment\":\"差评\"}" $B/api/v1/visitor/ratings; done
  curl -s $B/api/v1/visitor/spots/1/ratings/stats
  # 不存在的景点也能评分：
  curl -s -b j.txt -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' -d '{"session_id":"x","spot_id":999999,"overall_rating":5}' $B/api/v1/visitor/ratings
  ```
- **静态推断的实际结果**：stats 的 `count` 增加 100，平均分被拉到接近 1；对不存在的 spot 999999 同样返回 `code:0`。
- **预期结果**：评分绑定真实的 `user_id`（游客也有），同一用户同一景点只能评一次；校验景点存在；限流；限制评论长度。
- **代码位置**：`internal/handler/visitor_experience_handler.go:20-32,64-70`；`internal/service/visitor_experience_service.go:104-135`；`internal/repository/visitor_experience.go:19-`。
- **修复建议**：路由加 `OptionalAuth + EnsureGuest`，唯一键改成 `(user_id, spot_id)`；`session_id` 由服务端从已校验归属的会话里取。

### S-7【中】RAG 多轮上下文不校验会话归属

- **原理**：`/ai/chat` 直接把 `req.SessionID` 传给 `QueryWithRAGStreaming` / `QueryWithRAGAndRouteTraceInSession`（`ai_handler.go:314-318,405`）。RAG 层 `LoadSessionHistoryFromDB` 调用 `GetRecentMessages`，而这个函数的注释写得很清楚：**"用于上下文构建，不校验归属"**（`chat_session_service.go:213-214`）。随后 `buildSessionContextText` 把历史拼进 prompt（`rag_service.go:938-950`）。持久化环节（`AddMessages → EnsureSession`）有归属校验，**读取环节没有**。非流式路径还会执行 `appendSessionTurn`（`session_manager.go:44`），把攻击者这一轮写进以该 `session_id` 为键的内存历史（`sessionHistory` 只按 session_id 索引，不区分用户），从而**污染会话主人后续的上下文**。
- **利用门槛**：Vue 前端用 `crypto.randomUUID()` 生成 session_id（`DigitalHumanView.vue:175-176`），很难猜；但旧版页面用 `'home_' + Date.now()`（`static/js/app.js:593`），可以按时间枚举。管理员接口和交互日志里也能看到 session_id。所以评为"中"。
- **复现步骤**：
  ```bash
  B=http://127.0.0.1:8080
  # 受害者 A（指纹不同）
  curl -s -c a.txt -H 'Content-Type: application/json' -d '{"device_fingerprint":"victim-fp-1"}' $B/api/v1/auth/guest-login >/dev/null
  CA=$(awk '$6=="csrf_token"{print $7}' a.txt)
  curl -s -b a.txt -H "X-CSRF-Token: $CA" -H 'Content-Type: application/json' -d '{"message":"我想带我八十岁的母亲去灵山大佛，她腿脚不好","session_id":"victim-sess-1"}' $B/api/v1/ai/chat >/dev/null
  sleep 2   # 等待异步持久化
  # 攻击者 C（另一个游客），使用受害者的 session_id
  curl -s -c c.txt -H 'Content-Type: application/json' -d '{"device_fingerprint":"attacker-fp-9"}' $B/api/v1/auth/guest-login >/dev/null
  CC=$(awk '$6=="csrf_token"{print $7}' c.txt)
  curl -s -b c.txt -H "X-CSRF-Token: $CC" -H 'Content-Type: application/json' -d '{"message":"那她适合走哪条路线？","session_id":"victim-sess-1"}' $B/api/v1/ai/chat
  # 对照：直接读消息接口会被拒绝
  curl -s -b c.txt "$B/api/v1/sessions/victim-sess-1/messages"
  ```
- **静态推断的实际结果**：攻击者的回答里带上了"母亲、腿脚不好"这类只存在于 A 历史中的上下文（追问改写 `RewriteFollowUpQuery` 会把上一轮的主题拼进检索语句）；而直接读取 messages 接口返回"无权访问该会话"，说明两条路径的校验不一致。配置了 LLM 时，可以用"请复述我刚才说的话"诱导模型复述对方内容。攻击者这一轮的持久化会失败（`AddMessages` 返回 `ErrSessionAccessDenied`，日志 `会话持久化失败`），但内存上下文已经被污染。
- **预期结果**：使用 session_id 之前先校验 `session.UserID == 当前 user_id`，不属于当前用户就当作新会话处理。
- **代码位置**：`internal/handler/ai_handler.go:314-318,405`；`internal/service/rag_service.go:938-950`；`internal/service/session_manager.go:22-44,122-167`；`internal/service/chat_session_service.go:213-219`；`internal/handler/ai_proxy_handler.go:162,168`、`digital_human_handler.go`（同样透传 session_id）。
- **修复建议**：`sessionHistory` 的键改为 `userID:sessionID`；`GetRecentMessages` 增加 `userID` 参数并校验归属；handler 层统一调用 `EnsureSession(sessionID, userID)`，失败就拒绝请求或生成新的 session_id。

### S-8【中】Redis 限流所有路由共用同一个计数 key

- **原理**：`RedisRateLimitMiddleware` 的 key 固定为 `ratelimit:<ClientIP>`（`middleware.go:152`），**不包含路由名或阈值**。但它被用在 `/track`（30 次/分钟，`routes.go:90`）、`/v1/chat/completions`（30，`routes.go:132`）和整个 `/admin` 组（60，`admin_handler.go:48`）上。同一个 IP 的所有请求累加到同一个计数器，各路由再拿自己的阈值去比较。管理大屏一次刷新要并发请求 9 个 `/admin/dashboard/*` 接口，再加上前端每次页面切换都会 `/track`，**管理员刷新 3~4 次就会被 429**，而且 `/track` 会先于 admin 被限死（阈值 30 < 60）。这个问题只在配置了 Redis 时出现；`config.example.yaml:65-66` 默认 `addr: "localhost:6379"`，本机装了 Redis 就会触发。
- 另外，admin 组的限流放在鉴权之前（`admin_handler.go:48-49`），未登录的扫描请求也会消耗管理员 IP 的额度。
- **前置条件**：运行一个 Redis（`docker run -d -p 6379:6379 redis:7`），启动日志里没有出现"Redis 连接失败"。管理员已登录（见 R0）。
- **复现步骤**：
  ```bash
  B=http://127.0.0.1:8080
  CSRF=$(awk '$6=="csrf_token"{print $7}' admin.txt)
  for i in $(seq 1 31); do curl -s -o /dev/null -w '%{http_code} ' -b admin.txt -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' -d '{"page":"/map","action":"visit"}' $B/api/v1/track; done; echo
  curl -s -o /dev/null -w 'admin overview: %{http_code}\n' -b admin.txt $B/api/v1/admin/dashboard/overview
  for i in $(seq 1 30); do curl -s -o /dev/null -w '%{http_code} ' -b admin.txt $B/api/v1/admin/dashboard/overview; done; echo
  redis-cli keys 'ratelimit:*'; redis-cli get "ratelimit:127.0.0.1"
  ```
- **静态推断的实际结果**：第 31 次 `/track` 返回 429；随后 admin 请求在累计计数超过 60 时开始 429，而这时 admin 实际只请求了约 29 次；Redis 里只有一个 key `ratelimit:127.0.0.1`。

### F-6【低】SSE 心跳竞态；`WriteTimeout=60s` 会切断长流

- **原理**：`ai_handler.go` 流式分支里，心跳 goroutine 用 `select` 同时等 `ticker.C` 和 `doneCh`。两者同时就绪时 Go 随机选一个，有可能在 handler 已经 `<-doneCh` 返回（gin 回收 Context/Writer）之后再往 `writer` 写一次心跳，属于数据竞争。另外 `http.Server.WriteTimeout = 60s`（`main.go:143`）作用于**整个响应**，LLM 慢、长回答或长文本 TTS 流超过 60 秒会被强制断开，15 秒一次的心跳解决不了这个问题。
- **复现思路**：用 `go test -race` 配合一个会阻塞 15 秒以上的假 RAG 服务；或者把上游 LLM 指向一个故意延迟 70 秒逐字输出的 mock 服务，观察连接在约 60 秒时断开（`curl: (18) transfer closed`）。
- **修复建议**：心跳写之前再检查一次 `doneCh`（在锁内用 `select { case <-doneCh: return; default: }`）；对 SSE/TTS 路由用 `http.ResponseController.SetWriteDeadline` 单独延长写超时。

### F-10【低】改用户名不查重，冲突时返回 500

- **原理**：`UpdateUser`（`user_handler.go:259` 起）改用户名时不检查重名，依赖数据库唯一索引报错，然后统一返回 `InternalError("msg_update_failed")`。用户看到"服务器错误"而不是"用户名已存在"；游客也能用这个接口改自己的用户名。
- **复现步骤**：注册 `userA`、`userB` 两个用户，用 userB 的登录态 `PUT /api/v1/users/<userB_id>`，请求体 `{"username":"userA"}` → 返回 500。
- **修复建议**：先 `FindByUsername` 查重，冲突返回 409；游客禁止改用户名（应走 upgrade-guest）。

## 附录 R0：云端复现环境准备（供云端代理 / 手动复现使用）

```bash
# 1. 获取代码（在云端 VM 内）
git clone https://github.com/4evour/Scenic_spot_guide_system.git && cd Scenic_spot_guide_system
# 2. 依赖：Go 1.25+、Node 22、sqlite3、jq、（S-8 需要）redis-server
# 3. 配置（SQLite，本地兜底，不需要任何第三方 key）
cp configs/config.example.yaml configs/config.yaml
export SCENIC_GUIDE_SECURITY_JWT_SECRET=$(openssl rand -hex 32)
export SCENIC_GUIDE_ADMIN_USERNAME=admin
export ADMIN_PW='AdminPass123' SCENIC_GUIDE_ADMIN_PASSWORD='AdminPass123'
# 不跑 S-8 时让 Redis 地址失效，走内存限流：
export SCENIC_GUIDE_REDIS_ADDR=127.0.0.1:1
# 4. 前端产物（F-3 的对照组先不执行这一步）
(cd web-vue && npm ci && npm run build)

curl -s -c admin.txt -H 'Content-Type: application/json' -d "{\"username\":\"admin\",\"password\":\"$ADMIN_PW\"}" http://127.0.0.1:8080/api/v1/login
CSRF=$(awk '$6=="csrf_token"{print $7}' admin.txt)
```

- 不需要 key 的模块：鉴权、会话、评分、限流、QR、管理 CRUD、本地 RAG 兜底都可以完整复现。需要外网或 key 的模块：Edge TTS（需要访问微软服务，不通时 S-3 仍能验证"无鉴权、无限流、无长度限制"）、LLM 生成（S-4 的"成本放大"部分可以用一个本地 mock 的 OpenAI 兼容服务代替，把 `SCENIC_GUIDE_AI_BASE_URL` 指向它并记录收到的 prompt 长度）。
