# 评委版演示视频文案与分镜

## 旁白

### 01 前景引入

景区导览的难点，不是展示信息，而是让游客获得可信、及时、可执行的下一步。

### 02 游客端引入

接下来从游客端开始，沿着地图、景点和路线，查看一次完整导览如何发生。

### 03 游客地图

进入游客地图后，页面首先呈现景区整体空间关系。编号节点对应景点，路线把分散位置串联成易于理解的游览顺序。游客可以点击节点查看景点详情，包括基础介绍、开放信息和服务提示；也可以根据当前位置和偏好选择推荐路线。页面的离线示意标签明确标注数据边界，不会把演示状态包装成实时线上数据。下方入口连接路线、景点列表和二维码导览，让游客从发现景点、了解内容到确定下一站，都在同一流程中完成。这里看到的地图、接口响应和页面状态，均来自当前本地运行项目。

### 04 AI 问答引入

当游客提出问题，系统将自然语言请求转换为检索、生成和上下文承接流程。

### 05 AI 问答

在数字人页面中，游客可以直接输入问题，例如询问灵山大佛的高度。请求进入后端后，系统先检索景区知识库，找到相关内容，再组织为可阅读的回答并流式返回。继续追问开放时间时，系统保留当前会话主题，避免把“它”理解成新的未知对象。界面同时提供推荐问题、路线偏好、景点评分和反馈入口，让问答不只停留在一段文字，交互过程因此更连贯。没有外部模型密钥时，系统会明确使用本地 BM25 检索降级，保证基础问答仍可用。这里展示的是实际运行链路，不把模型生成等同于检索准确率，也不隐藏降级边界。

### 06 数字人边界

左侧 Live2D 形象呈现数字人状态，右侧保留文字输入、推荐问题和路线选择。项目重点是协议适配与前端交互二次开发。连接状态、文本回答、打断控制和服务降级，都在同一界面中表达。外部数字人服务不可用时，页面仍可切换到 Go 端 RAG 链路继续问答。这里不把外部框架包装成从零自研。

### 07 运营闭环引入

游客侧产生的提问、评分与反馈，将回到运营端，形成内容持续改进的依据。

### 08 数据大屏

进入数据大屏，运营人员可以看到服务人次、问答次数、满意度、响应延迟和知识库条目数量。下方展示热门景点、问答关键词与人流热力，帮助判断游客关注点和服务状态，也为后续内容调整提供直观依据，让运营判断更加集中。所有指标来自当前本地演示数据，用于证明看板和接口链路可以运行，不代表真实商业运营数据。

### 09 知识库管理

知识库管理页把 RAG 内容维护落实到具体操作。顶部显示条目数量、当前结果、支持格式和缓存状态。运营人员可以按标题检索，填写分类、来源和正文，也可以上传 JSONL、JSON、Markdown 或文本文件批量导入。内容保存后进入知识库，成为后续检索与回答的依据。这里展示已有管理接口，不绕过人工审核。

### 10 游客问题处理

游客问题页集中承接需要人工处理的问答和反馈。运营人员可以在未回答与全部问题之间切换，刷新列表并查看处理状态。出现知识缺口时，问题可以被回复、编辑并标记为已处理，再进入内容维护流程。当前演示数据没有待办，因此页面如实显示空状态；系统不会用自动闭环替代人工审核。

### 11 技术收束

游客导览、检索增强问答与运营维护，形成可运行、可解释、可复现的闭环。

## 字幕规则

- 每条字幕最多两行，每行不超过 24 个中文字符。
- 字幕与旁白逐句同步，位于画面下方，每句优先控制在 22 个中文字符以内。
- 解释卡只保留一个主标题和一句补充说明，标题使用薄荷绿或琥珀色证据标签。
- 不将 API Key、Cookie、数据库路径、真实日志或未验证外部服务状态写入字幕。
